# 품질 게이트

## 통과의 의미

스키마 검증은 문항의 형식을, 계산 검증은 제출된 식의 산술을 검사합니다. 둘 다 문항의 정답 타당성을 증명하지 않습니다. 블라인드 풀이와 편집 검토를 통과해도 상태는 `awaiting_human_review`입니다.

| 단계 | 점검 | 실패 시 |
|---|---|---|
| 명세 | 시험·급수·과목, 수량, 단독/2문항 세트 | 작성 전 중단 |
| 자료 | 출처 ID, 전문/통계, 분류 체계, 결손 | 미확인 부분을 명시 |
| 기계 검사 | 5지선다, 선지 중복, 판정 누락, 표 크기, 정확한 분수 계산, 해설 직접 인용 | 수정 필요 |
| 독립 풀이 | 출제 정답 미공개, 전 선지 판정, 유일성, 부족 조건 | 수정 필요 |
| 편집 | 문체, 정보량, 시험 적합성, 정의·수치 전사, 독창성 | A/B 해결 후 재검토 |
| 사람 검토 | 실제 풀이 시간·정답률, 이의 제기, HWP 시각 확인 | 납품 여부 판단 |

## 수정 이력 회귀 항목

1. 날짜 삭제: 기간 기산점, 만료 시각, 이의 시점을 모두 닫았는가?
2. 판단 불가: 어떤 견해가 침묵하면 반대 견해라고 처리하지 않았는가?
3. 정의 변경: 감소량/남은 양, 비중/증가율, 충분/필요를 바꾸지 않았는가?
4. 해설 동기화: 현재 없는 문장을 인용하거나 삭제한 조문을 쓰지 않는가?
5. 과잉 압축: 없어도 되는 설명과 정답에 필수인 조건을 구별했는가?
6. 난도: 계산량·생소한 개념의 수로만 높이지 않았는가?
7. 독창성: 기출의 소재·이름·숫자만 바꾼 문제가 아닌가?

1·2·3·5·6·7의 의미 판정은 모델 또는 사람의 업무입니다. 단위 테스트가 이를 일반적으로 해결한다고 주장하지 않습니다. 날짜·배치·최적화의 범용 제약해결기는 아직 없으며, 필요하면 문항별 독립 검증기를 작성합니다. 모델이 생성한 임의 Python 코드를 자동 실행하지 않습니다.

## 평가 계획

먼저 각 제품·과목에서 10~20개를 만들어 초안과 최종본의 A급 오류율, 사람 수정 시간, 채택률, 실제 풀이 시간을 기록합니다. 동일 문항의 여러 버전은 훈련/참고와 평가에 나누어 넣지 않습니다. 회차·문항군 단위로 분리하고 검토자가 원문과 정답을 미리 본 사례를 표시합니다. 소규모 팀 검토 정답률은 공식 응시자 전체 통계로 표현하지 않습니다.

생산 가능량은 생성 속도보다 사람 검토 병목으로 산정합니다. API 미실행 상태에서는 회차 생산량이나 월 납품 수를 추정값으로 확정하지 않습니다.
