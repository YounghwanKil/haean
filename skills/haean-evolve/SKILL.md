# 해안 개선 루프

저장소 `evals/protocol.md`, `evals/rubric.md`를 읽는다. 사용자가 요청한 개선 범위와 실행 예산을 따른다. 별도 예산이 없으면 한 차례의 후보 비교부터 시작하고 무한 반복하지 않는다. 기본 모델은 사용자가 요청한 Astra다.

핵심 입력은 자유로운 텍스트 피드백이다. `scripts/haean-tool feedback-notes --exam EXAM --subject SUBJECT`로 해당 제품군과 공통 의견을 읽고, 문항별 `feedback.jsonl` 및 연결된 버전도 확인한다. 사람·모델 의견을 구분하고 원문을 지우거나 미리 요약으로 대체하지 않는다. 각 의견을 오류, 표현 취향, 해당 문항의 국소 수정, 일반화 가능한 지침 후보로 분류한다. 상충하는 의견은 문면·반례로 판별하고, 반영·보류·반박 이유를 남긴다. 근거 문항이 없으면 가설로만 취급한다.

baseline이 없으면 요청 범위의 pilot 1~2과제로 먼저 실행 상태와 기준 결과를 만든다. 자료가 없으면 필요한 시험 자료를 구체적으로 알리고 원문을 꾸미지 않는다. 이미 쓰는 평가가 있으면 과제·수정 예산·모델을 재사용한다.

## 반복 단위

1. baseline 평가 결과와 원문 출력·수정본·독립 풀이·윤문 기록을 확인한다. 숫자 요약만 읽지 않는다. 같은 실패가 어느 단계에서 생겼는지 가설을 쓴다.
2. `scripts/haean-tool experiment NAME --baseline BASELINE_JSON`으로 실험 디렉터리와 동결 파일 해시를 만든다. `proposal.md`에 근거 사례, 변경 대상, 기대 효과, 퇴행 위험을 남긴다.
   텍스트 피드백에서 출발했다면 피드백 ID·작성 주체·문항 해시, 재현 가능한 실패, 기대할 변화, 반영하지 않은 의견의 이유도 함께 남긴다. 만족스러운 문장으로 바뀌었다는 인상과 정답 타당성·오답 기능의 변화를 분리한다.
3. **haean_optimizer 서브에이전트에 후보 패치를 위임한다.** 실험용 브랜치/별도 작업 폴더에서 `skills/`, `src/haean/prompts/`, 검색·문항 생성 코드만 고친다. `evals/`, 평가 코드, holdout, 기존 점수·출력은 고치지 않는다.
4. 동일 과제·모델·수정 예산으로 후보를 실행하고 `evaluate`와 `compare`로 비교한다. 개발 평가에서 개선이 보인 후보만 별도 편집자에게 봉인 평가를 요청한다.
5. 고정 평가의 변경, 문항 수 감소, 실행 실패 누락, 틀린 정답을 맞게 보이도록 채점 기준 수정은 개선으로 인정하지 않는다. A급 오류와 제품군별 퇴행을 평균 점수로 가리지 않는다.
6. 코드 diff, 원문 기록, 점수, 실행 시간·토큰, 전문가 의견을 보존하고 후보의 채택/기각/보류 이유를 남긴다. 현재 프로토콜에서 자동 비교 결과는 후보 추천이며 전문가 검증을 뜻하지 않는다.

반복 중 사용자가 중단하면 실행을 멈추고 재개 지점을 남긴다. 평가자가 모델이고 전문가 패널이 없으면 성과를 '모델 평가상 개선 신호'로 표현한다. 실제로 평가하지 않은 과목이나 납품 양식까지 잘 된다고 일반화하지 않는다.

역할 선택 인자가 없는 위임 도구에서는 `role haean_optimizer`로 읽은 지침을 일반 서브에이전트의 작업 메시지로 전달한다. 후보는 별도 폴더에 저장하고 평가할 때만 적용하며, 비교 후 채택 전에는 baseline을 복원한다. 개선 후보가 점수상 퇴행하면 원본 지침으로 돌아가고 원문 기록과 패치는 남긴다. 평가에 쓰이지 않는 스킬만 변경한 뒤 프롬프트 파이프라인 점수로 그 스킬의 효과를 주장하지 않는다.

이는 [Meta-Harness](https://arxiv.org/abs/2603.28052)의 실행 기록 기반 외부 개선 루프를 출제에 적용한 설계다. 논문의 벤치마크 성과가 해안 문항 생성에서도 재현됐다고 주장하지 않는다.
