# 해안 평가 프로토콜 v2

v2는 자료해석의 기계 검증에서 지문·보기에 있는 실제 막대/선그래프도 원자료로 인정한다. 표 또는 해당 수치 그래프와 재계산 명세가 있어야 한다. 선지에만 있는 그래프, 논증 도식, 그림에 대한 텍스트 설명은 이 원자료 검사를 대신하지 않는다. 그래프의 범주·계열은 문항 스키마로 검증하고 실제 수치·의미·이미지는 독립 풀이·편집 검토에서 확인한다. 표 없는 실제 선그래프가 일률적으로 거부된 개발 사례를 고치는 변경이며 점수 척도와 품질 기준은 유지한다.

v1로 실행한 결과의 점수·채택률을 v2 결과와 직접 비교하지 않는다. baseline과 candidate를 동일한 v2 아래 다시 실행하기 전에는 성능 향상이나 후보 채택을 주장하지 않는다. 기존 실행·원문·검토는 보존한다.

목표는 LEET·PSAT의 실제 출제 품질이다. 평균 점수가 높아도 정답 오류가 있는 문항은 채택하지 않는다. 모델이 스스로 매긴 점수만으로 전문가 수준이라고 선언하지 않는다.

## 평가 단위와 자료 분할

LEET 추리논증, PSAT 5급 3과목, PSAT 7급 3과목을 **7개 제품군**으로 나눠 보고한다. 한 제품군의 개선으로 다른 제품군의 퇴행을 상쇄하지 않는다. 단독 문항과 공통지문 세트도 분리한다.

- pilot: 실행·진단용 공개 과제. 현재 포함된 7개 과제는 개발자가 작성한 출제 요청이며 전문가 인증 벤치마크가 아니다.
- development: 실패 분석과 하네스 수정을 허용하는 과제. 최초에는 제품군별 10~20개를 모아 평가자와 팀 기준을 맞춘다.
- holdout: 편집자가 별도 보관하는 미공개 과제와 전문가 판단. 원문·변형·수정본은 같은 문항군으로 묶어 같은 분할에 둔다. 현재 저장소에는 이 데이터가 없다.

기출을 풀이 평가에 쓰는 경우 검색 DB에서 해당 원문·변형·해설을 제외해야 한다. 본 파일의 pilot은 새 문항을 생성하는 평가다. 같은 기출 풀이 점수를 출제 품질로 대체하지 않는다.

## 한 과제의 실행

1. 요청, 데이터 지문군/분할, 하네스 전체 파일 해시, 모델 ID, Codex 버전, 시각을 고정한다.
2. Astra로 초안을 생성하고 원문과 실행 로그를 보관한다.
3. 문체 윤문을 적용한 경우 원문·윤문본·변경 구간·im-not-ai 게이트를 함께 남긴다. 윤문 여부도 실험 조건이다.
4. 정답·해설·출처 없이 새 컨텍스트에서 전 선지를 푼다. 풀이 실패와 복수 해석을 숨기지 않는다.
5. 편집 검토자가 현행 문항·풀이·해설을 대조한다. 의미 검토와 기계 검증을 구분한다.
6. 수정은 최대 2회. 최초 초안과 최종본을 각각 평가해 개선 비용을 측정한다.
7. 동결된 rubric으로 독립 평가하고 원문 근거를 남긴다. 실제 팀 검토 결과는 별도 human review로 저장한다.

## 점수와 채택

첫 번째 지표는 A급 오류율, 독립 정답 불일치율, 조건 부족/복수정답률이다. 유효성에 실패하면 `eligible=false`이며 문체 점수로 보상하지 않는다. 정합성을 통과한 문항에서만 시험 적합성·논증 가치·오답 품질·문장·독창성·부담을 비교한다.

각 차원은 0–4의 근거 있는 서열 척도다. 0=사용 불가, 1=전면 수정, 2=상당 수정, 3=경미 수정, 4=관찰한 결함 없음. 4는 오류가 없다는 수학적 증명이 아니다. 소수점 점수의 작은 차이를 실제 향상으로 해석하지 않는다.

사람 검토에는 검토자, 문항 해시, 정답 동의, 오류 등급, 채택 여부, 수정 시간, 실제 풀이 시간, 문체/시험 적합성 의견을 기록한다. 최소 두 전문가의 판단 충돌을 조정한다. 평가자에게 어느 버전이 후보인지 가리고 A/B 순서를 바꾼다. 정답률은 실제 응시 표본과 모집단을 함께 기록한다.

## 하네스 후보 비교

같은 과제·모델·수정 예산·윤문 여부로 baseline과 candidate를 비교한다. 초기에는 과제당 최소 3회 반복하고 제품군별 분포를 보고한다. 짝지은 차이와 채택률, 수정 시간, 실행 시간·토큰 사용량을 함께 보고한다. 작은 pilot에서 나온 점수 차이는 개선 신호이지 통계적 증거가 아니다.

평가기 코드·rubric·과제·비교 규칙은 실험 도중 동결한다. 이를 고치면 새 프로토콜 버전으로 양쪽을 다시 평가한다. optimizer는 development의 코드·출력·실패 기록을 읽을 수 있지만 holdout 정답·전문가 메모를 읽지 않는다. 같은 컴퓨터의 폴더 구분은 보안 격리가 아니므로 봉인 평가는 별도 계정/환경에서 수행한다.

자동 루프는 개선안 생성·패치·개발 평가·후보 순위까지만 수행한다. 전문가 기준이 교정되기 전 기본 하네스의 채택은 사람 검토 후 진행한다. 실행 예산에 도달하거나 동일 오류가 반복되거나 개선이 없으면 멈추고 원인과 다음 실험을 기록한다.
